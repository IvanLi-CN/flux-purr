# Heater PID frontpanel runtime implementation

## Current coverage

- PID heater control, fan policy, fault latching, dashboard state projection, and frontpanel runtime synchronization are implemented.
- Dashboard startup presentation uses explicit initializing, EEPROM-restore, ready, and initial-RTD-fault states so the first framebuffer cannot expose a numeric bring-up placeholder. PD readiness is represented separately as `POWER/WAIT`; the fixed post-display and pre-ADC delays are removed from the Dashboard path.
- The async display SPI device owns CS through a drop guard, so a PD-service timeout cannot leave the panel selected. USB early-control emits `boot_stage=runtime_ready` only after the first UI and startup work have completed, before the runtime loop begins.
- Host fixtures and web/native contracts cover normal operation, cooling, over-temperature, sensor faults, and safe-off behavior.
- The normalized heater/fan state is shared across firmware, devd, HTTP, and Web surfaces.
- The separate `pps5a` thermal-tuning runtime records local samples and installs candidate RAM previews at trial boundaries. Normal 5A heating and tuning select the same existing point-local profile controller when a valid physical model and verified 5A-capable source are present. Host tests show that changing a candidate approach point changes the logical request, a 3A source retains plant-PI output, and an armed source-class change disarms before the controller changes. Preview identity, basic safety disarm, and a 60-second hold trace have host coverage. Device samples now confirm logical requests and final MOS PWM during 60°C and 240°C trials, but complete qualification remains unproven.
- A tuning run begins with a heater-off cooldown and PPS staging check. MOS stays at zero while the automatic PPS request steps toward the selected APDO ceiling; cooldown samples remain in the event trace, and warmup begins only after both the request and confirmed contract reach that ceiling and the temperature threshold is met. Device event time is relative to the run command, and missing or broken stable-window evidence rejects the trial at the full-speed-to-stable deadline. Each target has a monotonic 20-minute budget including cooldown and power staging, with no separate two-trial cap; safety faults still disarm immediately.
- In the default nine-target scope, failed endpoints do not suppress the other endpoint. An interior target runs only when both recursive parent bounds were accepted; otherwise it records an interval-prune decision without heating. Eligible interior targets seed their point from the two accepted bounds, update the canonical candidate hash, and require a new RAM preview receipt at the next trial boundary.
- Trial warmup evidence requires a first sample with at least 99.5% logical request and 99% physical PWM; after that point the logical request must remain full. A physical dip may remain between 95% and 99% for at most two seconds. Lower or longer dips invalidate the trial's warmup gate, while pre-full soft-start samples do not claim full-output evidence.
- Trial decisions record the external strategy's eleven ordered score dimensions using device-local evidence. Hold PWM percentiles and the fitted approach-curve error are accumulated from the trial's own samples; missing evidence receives the explicit worst-rank sentinel rather than an invented measurement. Each target uses separate 12-second scout, current/predicted batch comparison and 60-second hold-confirm trials, with cooldown and trial-local metrics between them.
- Device-local first-band and deadline evidence now selects the external strategy's conservative high-side candidate before a conflicting underpowered-curve adjustment. A focused runtime regression replays the observed 60°C high-side temperature path and verifies the next RAM-preview candidate moves braking and approach energy in the conservative direction. A separate strategy fixture covers the completed, stable-window-verified small hold-ripple trim. Firmware host tests and both ESP32-S3 release configurations build; this candidate-selection correction has not yet been verified on the physical device.
- Tuning interlock failures now distinguish PD-contract loss, persistence, thermal-model, cooling, controller, and sensor gates in the device safety event; these interlock failure paths clear the RAM preview. This diagnostic behavior has host-test and firmware-build coverage, and the diagnostic firmware identity has been read back from the device; a 5A trial has not yet exercised the new failure attribution.
- The firmware CLI accepts an ordered subset of the frozen nine 5A targets for diagnostic retests. The device receives the filtered recursive order, while the standard five-file report retains the complete physical target set and marks the selected subset as `diagnosticOnly`; even a successful device-local subset cannot qualify or be explicitly saved. The host watchdog covers the device's fixed 20-minute budget for each selected target plus a bounded finalization margin.
- After a running event read fails, the CLI cancels first, verifies the same disarmed run, and drains its retained terminal events within 120 seconds and the device's bounded retention capacity. Each page reaches the durable journal before the next ACK; a final ACK confirms a complete tail. Transport-timeout regression tests cover both recoverable tails and overwritten events. Recovery preserves the failed owner outcome and host interruption rather than promoting a canceled run into qualification evidence.
- The firmware CLI journals preflight and five-second runtime snapshots through the same device lease in `device-runtime-statuses.ndjson` beside its raw event journal. Each snapshot retains the run ID, durable event cursor, host receipt time and unmodified device status, including temperature, fan commands, MOS output and uptime. These snapshots remain raw input evidence; the five-file report and trial sample stream are unchanged, and fan commands do not claim tachometer measurements or verified fan rotation.
- The standard v2 renderer preserves device target-level budget-exhaustion decisions in attempted-target summaries without replacing individual trial stop reasons. A replay of the device-local 60°C and 240°C failure events keeps both endpoint failures, the 523,711 ms inter-trial cooldown, and the rejected 240°C hold confirmation distinct.
- Thermal tuning retains an admitted automatic PPS ticket through its terminal outcome. A `WaitingForAccept` / `WaitingForPsRdy` snapshot is a bounded pending state, not a tuning failure; PWM remains off until an exact PPS voltage/current confirmation is consumed. The caller bounds each 500 mV ticket from its own admission time rather than timing the whole multi-ticket staging ramp against the first ticket; the full ramp still consumes the target's 20-minute budget. Rejection, timeout, transport fault, detach, supersession, or an exact-contract mismatch routes to the existing safe fallback and cannot produce a passing tuning result. The PD service projection remains responsible for deciding whether a previously confirmed contract is still observable during a transition; changing that projection is a separate PD approval boundary.

## Validation

- Firmware host tests, web unit tests, and frontpanel preview fixtures cover the runtime state model.
- Safety paths retain fail-closed behavior when sensor, control, or transport checks fail.
- Host-side frontpanel preview and state-transition tests cover placeholders, EEPROM restore, PD wait, initial sensor fault, first valid RTD promotion, and preservation of the last valid temperature after runtime faults.

## Remaining gaps

- Physical thermal-loop acceptance requires a complete passing authorized device run, including the default nine-target scope and verified save receipt.
- Authorized device HIL with firmware `0.27.6-dev.ebbecfb` established a 21V/5A-capable PPS path and produced a complete, digest-verified five-file failure report. The 60°C cooldown staged successive 500 mV requests and every observed contract confirmation matched the requested voltage through 20.5V, with MOS PWM held at zero as required. The caller then timed out the whole staging ramp at sequence 30 because it reused the first ticket's wait origin, even though the latest ticket was still within its own bounded wait. The heater disarmed, the candidate was rejected, and no profile was saved; this report is not qualification evidence.
- Authorized device HIL with firmware `0.27.6-dev.07e0ac2` passed the former shared-ticket timeout boundary, then remained in the 60°C heater-off cooldown with a 21V request, a 20.5V runtime contract projection, VIN near 21.3V, and zero MOS PWM. The run was canceled safely after the mismatch persisted for more than ten minutes; its five-file report has a complete, digest-verified trace, no accepted target, and no saved candidate. The display and heater runtime had shared one latest-value PowerState receiver, so display refresh could consume an update without advancing the heater runtime's PowerState.
- Authorized device HIL with firmware `0.27.6-dev.e628a25` confirmed that separate display and thermal subscriptions let the 60°C cooldown observe the exact 21V/5A PPS contract and enter warmup with MOS PWM applied. An initial warm device stayed above the frozen 35°C cooldown threshold; a five-minute power-off cooldown allowed a full-scope retry to begin at 32.71°C. Two 60°C trials failed the full-speed-to-stable gate, with overshoot 3.11/3.30°C and hold peak-to-peak 5.21/5.44°C. The next predicted candidate could not begin before the 20-minute target budget expired because powered cooling settled above 35°C. The 240°C scout and 60-second hold-confirm trials passed; the adopted trial measured 0.28°C overshoot, 2.94°C hold peak-to-peak and 4417 ms full-speed-to-stable against a 5000 ms limit. Missing the accepted 60°C endpoint pruned the seven interior targets. The complete, digest-verified five-file report correctly concludes `failed`, rejects the candidate, and has no EEPROM save receipt; the device returned to idle at 12V/5A with MOS PWM zero.
- The firmware-owned 60°C cooldown uses the approved 40°C gate for initial and retry trials. Device `candidate_trial` records carry the measured boundary temperature and applied threshold; the standard five-file renderer presents them per selected trial and marks historical records without these fields `unavailable_device_trial_record`. Focused firmware, CLI, renderer and external-runner regression tests pass, and the Xtensa release image builds. Strict Xtensa Clippy is blocked by two pre-existing function-length findings in the unchanged `thermal_tuning_strategy.rs`.
- Authorized device HIL with firmware `0.27.6-dev.f47ab23` verified the 40°C boundary on five started 60°C trials: measured starts were 34.70, 39.98, 39.99, 39.85 and 39.96°C, all with a recorded 40.00°C threshold. The next retry did not start before the 20-minute target budget expired. Four trials missed the full-speed-to-stable gate and one missed the 3°C hold peak-to-peak gate. The 240°C endpoint had thirteen rejected trials, mostly without a stable window inside its 5-second limit; seven interior targets were pruned without heating because the endpoints were not accepted. The standard five-file report for run `firmware-pps5a-1790761275866` has a complete, digest-verified sequence 0–6936 and concludes `failed`; the candidate was rejected without EEPROM save. Device readback after the run confirmed idle mode, heater disabled and physical output zero, with the prior saved profile still active. This proves the cooldown exception and failure recording, not nine-target qualification.
- Candidate transformations and eleven-dimension batch ranking have targeted host fixtures, but full differential conformance against the frozen external 5A strategy remains unproven. A passing default-scope run, safe-failure coverage, and an EEPROM readback receipt are still required before qualification.
