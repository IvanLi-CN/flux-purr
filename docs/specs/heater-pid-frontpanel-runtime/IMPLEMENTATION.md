# Heater PID frontpanel runtime implementation

## Current coverage

- The verified 5A production profile supplies the same effective global settings to the PID and heater-output adapter, including the adjustable working-voltage floor and current reserve. Normal heating and tuning use saved/preview settings even when calibration is off; 3A plant control retains default output settings and calibration retains its existing profile selection. Host regressions cover these boundaries. Authorized HIL with firmware `0.27.6-dev.edc9175` read back the candidate's 6100mV floor and 300mA reserve while heating at 5A with HOT=LOW. The diagnostic run was canceled after targeted checks and retains device-verified sequence 0–1499; it does not establish qualification, and PPS Approach behavior and 20Hz cadence remain unresolved.
- The heater-output adapter distinguishes the profile controller's first Approach from its recovery after Hold. First Approach uses the existing bounded automatic PPS down-ramp; Hold and recovery retain the existing handoff-voltage governor. A same-APDO 5A adjustment with a valid continuous PowerState and no blank-heater requirement keeps the controller and trial recording active while the output adapter consumes the ticket. Initial cooldown staging and blanked transitions remain heater-off waits; ticket timeout and failed outcomes cannot use this continuity path. These guards consume existing production state without changing the PD service, protocol, PowerState, or 3A plant path. Authorized HIL with firmware `0.27.6-dev.dc82a1d` records continuous Warmup/Approach/Hold trials while PPS descends from 21V to 18V and 17.5V. The diagnostic run retains device-verified sequence 0–503 and was canceled after targeted checks. Its two 60°C trials remain rejected with 5.02°C and 3.95°C overshoot; it does not establish qualification.
- ADC conversions that become ready within 50 microseconds are polled without a timer wakeup. Slower conversions retain the asynchronous retry and existing fault path; discarded conversions yield in bounded groups. The calibrated discard/retained sample counts, phase averaging and settle delay are unchanged. The control deadline uses the current monotonic time after input processing rather than a pre-input timestamp. Host regressions cover fast-ready polling, bounded slow polling and conversion errors. Authorized HIL with firmware `0.27.6-dev.f6cef42` retained 205 runtime snapshots: the measured sensor/control/output segment was 40–65ms (mean 44.36ms), while consecutive control starts were 49–94ms apart (mean 63.73ms). These are five-second status snapshots rather than an exhaustive cycle histogram. The shorter segment does not establish the required 50ms cadence; thermal qualification remains incomplete.
- PID heater control, fan policy, fault latching, dashboard state projection, and frontpanel runtime synchronization are implemented.
- Dashboard startup presentation uses explicit initializing, EEPROM-restore, ready, and initial-RTD-fault states so the first framebuffer cannot expose a numeric bring-up placeholder. PD readiness is represented separately as `POWER/WAIT`; the fixed post-display and pre-ADC delays are removed from the Dashboard path.
- The async display SPI device owns CS through a drop guard, so a PD-service timeout cannot leave the panel selected. USB early-control emits `boot_stage=runtime_ready` only after the first UI and startup work have completed, before the runtime loop begins.
- Host fixtures and web/native contracts cover normal operation, cooling, over-temperature, sensor faults, and safe-off behavior.
- The normalized heater/fan state is shared across firmware, devd, HTTP, and Web surfaces.
- The separate `pps5a` thermal-tuning runtime records local samples and installs candidate RAM previews at trial boundaries. Normal 5A heating and tuning select the same existing point-local profile controller when a valid physical model and verified 5A-capable source are present. Host tests show that changing a candidate approach point changes the logical request, a 3A source retains plant-PI output, and an armed source-class change disarms before the controller changes. Preview identity, basic safety disarm, and a 60-second hold trace have host coverage. Device samples now confirm logical requests and final MOS PWM during 60°C and 240°C trials, but complete qualification remains unproven.
- A tuning run begins with a heater-off cooldown and PPS staging check. MOS stays at zero while the automatic PPS request steps toward the selected APDO ceiling; cooldown samples remain in the event trace, and warmup begins only after both the request and confirmed contract reach that ceiling and the temperature threshold is met. Device event time is relative to the run command. Scout and current/predicted batch trials collect their complete 12-second hold evidence even when the full-speed-to-stable gate fails, matching the external strategy; their failed gate still rejects the candidate. Final hold-confirm trials stop early when a qualifying stable window is no longer possible. Each target has a monotonic 20-minute budget including cooldown and power staging, with no separate two-trial cap; safety faults still disarm immediately.
- The 60°C firmware tuning target starts initial and retry trials only at or below 35°C. Cooldown forces the full-voltage fan command throughout the temperature and PPS wait, independently of ordinary post-heat modes. Terminal cooling after a 60°C scope retains that command until valid temperature is below 35°C; exactly 35°C does not release it. Other targets retain the 40°C terminal release threshold. Invalid temperature cannot release the cooling latch. Boundary and fan-command regressions cover these boundaries; authorized device HIL confirms all 60°C starts met the 35°C gate and full-fan/MOS-off was observed throughout active cooldown.

Run `firmware-pps5a-1790952587626` started all eight trials at `32.63..34.99°C` against the recorded `35.00°C` gate. Across 3,016 cooldown samples, logical and physical heater output remained zero; 169 runtime snapshots correlated to cooldown events all reported full fan and no command violations. The standard five-file report has complete sequence `0..3702`, verified device trace digest `8715ea70efeaa405810c8e1111df79ef25b2f2f658ecf1b6ae02b6134f748a4d`, and rejected the candidate without EEPROM save. - In the default nine-target scope, failed endpoints do not suppress the other endpoint. An interior target runs only when both recursive parent bounds were accepted; otherwise it records an interval-prune decision without heating. Eligible interior targets seed their point from the two accepted bounds, update the canonical candidate hash, and require a new RAM preview receipt at the next trial boundary.
- Trial warmup evidence requires a first sample with at least 99.5% logical request and 99% physical PWM; after that point the logical request must remain full. A physical dip may remain between 95% and 99% for at most two seconds. Lower or longer dips invalidate the trial's warmup gate, while pre-full soft-start samples do not claim full-output evidence.
- Trial decisions record the external strategy's eleven ordered score dimensions using device-local evidence. Hold PWM percentiles and the fitted approach-curve error are accumulated from the trial's own samples; missing evidence receives the explicit worst-rank sentinel rather than an invented measurement. Each target uses separate 12-second scout, current/predicted batch comparison and 60-second hold-confirm trials, with cooldown and trial-local metrics between them.
- Candidate analysis retains temperature, residual heat, PWM percentiles and recovery samples from the controller's first Hold phase, independently of the physical qualification hold gate. The 12/60-second timers and hold peak-to-peak acceptance metrics begin only at the physical gate. A real 60°C scout replay compares the firmware runtime's predicted candidate with the existing external strategy and covers the previously omitted early-Hold evidence; this differential result does not establish complete strategy conformance or device qualification.
- The predicted candidate applies the frozen external strategy's low/high-side stability-gate correction and bounded low-temperature step after its base transformation. Device-local band-entry, band-exit, deadline temperature and stable-window timing determine the gate class; overshoot and hold ripple determine eligibility for the bounded accelerated step. Hold-ripple and conservative high-side candidates retain their existing precedence. Five real 60°C trial replays compare the public firmware runtime's complete next point with the external strategy; the lower-band replay from firmware `0.27.6-dev.577a1c8` exposed the previously omitted correction. The correction has not yet passed device qualification.
- Device-local first-band and deadline evidence now selects the external strategy's conservative high-side candidate before a conflicting underpowered-curve adjustment. A focused runtime regression replays the observed 60°C high-side temperature path and verifies the next RAM-preview candidate moves braking and approach energy in the conservative direction. A separate strategy fixture covers the completed, stable-window-verified small hold-ripple trim. Firmware host tests and both ESP32-S3 release configurations build; this candidate-selection correction has not yet been verified on the physical device.
- Tuning interlock failures now distinguish PD-contract loss, persistence, thermal-model, cooling, controller, and sensor gates in the device safety event; these interlock failure paths clear the RAM preview. This diagnostic behavior has host-test and firmware-build coverage, and the diagnostic firmware identity has been read back from the device; a 5A trial has not yet exercised the new failure attribution.
- The firmware CLI accepts an ordered subset of the frozen nine 5A targets for diagnostic retests. The device receives the filtered recursive order, while the standard five-file report retains the complete physical target set and marks the selected subset as `diagnosticOnly`; even a successful device-local subset cannot qualify or be explicitly saved. The host watchdog covers the device's fixed 20-minute budget for each selected target plus a bounded finalization margin.
- After a running event read fails, the CLI cancels first, verifies the same disarmed run, and drains its retained terminal events within 120 seconds and the device's bounded retention capacity. Each page reaches the durable journal before the next ACK; a final ACK confirms a complete tail. Transport-timeout regression tests cover both recoverable tails and overwritten events. Recovery preserves the failed owner outcome and host interruption rather than promoting a canceled run into qualification evidence.
- The firmware CLI journals preflight and five-second runtime snapshots through the same device lease in `device-runtime-statuses.ndjson` beside its raw event journal. Each snapshot retains the run ID, durable event cursor, host receipt time and unmodified device status, including temperature, fan commands, MOS output and uptime. These snapshots remain raw input evidence; the five-file report and trial sample stream are unchanged, and fan commands do not claim tachometer measurements or verified fan rotation.
- The optional `fan-observe` build reads GPIO35/36 through their enabled digital input buffers and exposes `fanPadObservation` in USB/devd status. It preserves the production fan command, output routing and timer configuration. Repeated observations at constant 0%/100% duty distinguish the physical digital endpoint from the software command; intermediate-duty snapshots do not establish waveform frequency or duty. Fan rail voltage and mechanical speed remain unmeasured. Standard builds omit the observation.
- The standard v2 renderer preserves device target-level budget-exhaustion decisions in attempted-target summaries without replacing individual trial stop reasons. A replay of the device-local 60°C and 240°C failure events keeps both endpoint failures, the 523,711 ms inter-trial cooldown, and the rejected 240°C hold confirmation distinct.
- Thermal tuning retains an admitted automatic PPS ticket through its terminal outcome. A `WaitingForAccept` / `WaitingForPsRdy` snapshot is a bounded pending state, not a tuning failure; PWM remains off until an exact PPS voltage/current confirmation is consumed. The caller bounds each 500 mV ticket from its own admission time rather than timing the whole multi-ticket staging ramp against the first ticket; the full ramp still consumes the target's 20-minute budget. Rejection, timeout, transport fault, detach, supersession, or an exact-contract mismatch routes to the existing safe fallback and cannot produce a passing tuning result. The PD service projection remains responsible for deciding whether a previously confirmed contract is still observable during a transition; changing that projection is a separate PD approval boundary.

## Validation

- Confirmation-failure reseeding has its own frozen external-strategy projection and nudge; scout/batch transformations remain separate. A differential replay of the 43 actual samples from run `firmware-pps5a-1790952587626`, trial 6, proves brake/Approach/floor/damping/lead `1280/350/180/3910/3` after the failed confirmation. Applying the scout transformation to that same evidence instead produced `1100/590/340/3730/5`; the following physical scout exceeded both overshoot and hold-ripple gates. The regression exercises the runtime's `HoldConfirm -> Cooldown -> Scout` boundary and compares every point field with the external confirmation path. Independent low-temperature high-side and high-temperature high/low-side vectors cover the dedicated nudges, cross-phase hold-threshold observation and rounded step boundaries. This replay proves strategy conformance, not physical qualification or EEPROM persistence.
- Firmware host tests, web unit tests, and frontpanel preview fixtures cover the runtime state model.
- Safety paths retain fail-closed behavior when sensor, control, or transport checks fail.
- Host-side frontpanel preview and state-transition tests cover placeholders, EEPROM restore, PD wait, initial sensor fault, first valid RTD promotion, and preservation of the last valid temperature after runtime faults.
