# 固件主控调优整改合同

## 范围、基线与状态

本合同锁定 `thermal tune --engine firmware` 的 `pps5a` 调优整改，不代表整改已经实现或实机验收通过。工作仅在当前工作区及当前分支进行，报告、构建和 HIL 输入输出留在该工作区。沿用 [交付合同](DELIVERY-CONTRACT.md) 的单 PR 范围与 merge-ready 交付目标。

“旧方案”的定义仅来自交付合同：`origin/main@d86a4eddccfc9d31cbe9b9cb2f2d597b8b525278` 的外部主控 5A full-batch 调优。生产热控兼容锚点 `ff4bf3876f548bc4ba6ac1e2cb87259f0d132422` 不作为调优策略基线。不得从原对话关联分支导入代码、fixture、报告或 HIL 证据。

整改起点为当前分支提交 `240549cbc2427c250e687dd9c900f360a0d24b0e`。本工作区的 `firmware/target/hil-return-original-bundle/` 保留待分析的实机报告；它不是通过证据。分析必须覆盖全部 trial，不能仅选一个看起来较好的 trial 推导修正。

条件延长的方向已确认，完整时间策略与延长候选的升格口径仍须按本文待定项收敛。收敛前，现行 [热控 SPEC](SPEC.md) 的停止与验收门禁继续生效；本文不得被用于宣称普通超时候选已经获准通过或保存。

## 旧方案事实锁定

以下事实必须从锁定提交读取，不能以当前分支的同名外部函数代替基线：

| 项目 | 基线事实 | 使用边界 |
| --- | --- | --- |
| Approach 保守下调 | 高侧修正规则保留至少 `100‰`；低温高侧分支还取不低于 `holdPowerPermille` | `10%` 是逻辑满量程的候选下限，不能称为 MOS PWM 的下限或所有分支统一推荐值 |
| Approach 上限 | 相应修正规则取至少 `approachFloor + 80‰`，最大 `1000‰` | 间距为 8 个百分点；100% 是允许的参数边界，不是推荐值 |
| 60°C 内置初始点 | `approachFloor=510‰`、`approachPower=590‰` | 是内置种子；指定 seed 或默认已接受 seed 可优先参与实际初始化，不能倒推每次运行都从该点开始 |
| 参考曲线 | 首选 `5s`、上限 `10s` | 参考曲线时长与实际 Approach phase、稳定窗口计时分别记录 |
| full-speed-to-stable | 首次离开 Warmup 后，目标 `<=150°C` 为 `10s`，更高目标为 `5s` | 约束有效稳定窗口的起点；窗口为连续 `10s`、目标 `±1.5°C`、至少 `3Hz` |
| scout 与确认 | `TuningScout` 不强制执行 stage-limit 停止，`HoldConfirm` 执行；scout 仍记录 gate 失败 | 延长采集失败证据不等于该候选可确认、通过或保存 |

源码依据为锁定提交中的 `thermal_flagship.rs`、`cli/thermal_workflow.rs`、`cli/thermal_model.rs` 和 `cli/args.rs`。基线没有已确认的统一 Approach 推荐上限，也没有自动放宽资格门槛的例外。任何补充推荐范围都须明确标为设计提案，不能冒充旧约定。

## 整改项与验收

### R1：核对完整旧方案一致性

- 将初始 seed 选择、插值、候选变换、scout/confirm 输入投影、score、gate、预算、重试和 accepted-target blocking 逐项对照锁定基线。
- 分别列出冻结基线、当前分支外部 runner、当前固件的差异；当前分支两个实现相同，不能证明与冻结基线相同。
- 对 scout 超时后的证据范围与固件硬停止保留的样本前缀单独说明；不得用固件停止后的样本证明固件当时已经满足门槛。
- 差异必须归为已获准边界、实现缺陷或待研判设计变更。未经研判不得把修改外部 runner 当成恢复一致性的方法。

验收：每个差异都有固定基线、同一输入、字段级输出比较和处置依据。正常、低侧 miss、高侧越带、稳定窗口中断、缺失 qualified Hold、确认失败、预算耗尽及区间阻断均有覆盖。修正后仍存在的有意差异必须明确列出，不声称全向量一致。

### R2：修正 Approach 候选搜索与交接证据

- 使用 R1 确认的分支下限与上限约束，分别记录候选配置、生产 effective floor 和真实逻辑请求；有效下限受 Hold 基线影响时必须显示该来源。
- 普通调优不搜索将整个 Approach 置零的极端方案。既有过冲保护和预测 coast 的零输出仍保持有效，不得为维持 10% 而覆盖保护。
- 高侧余热、低侧缺口和 Hold 波动按完整证据分别修正。需要减少储热时，审查预热退出位置、brake/lead、Approach 上限、floor、damping 的联合影响；不得忽略交接及其它参数而把所有失败归为单一功率不足，也不能为了绕过期限放宽 Hold 入口。实验须保持可归因性，不在同一次失败中无差别搜索全部字段。
- 继续使用同一生产控制器。新增温度/升温率交接门禁、修改控制公式或阶段职责属于设计变更，须单独展示差异和验收影响。
- Hold 控制 phase、qualified Hold 起点和稳定窗口必须分别认定；不得将提前进入控制器 Hold 作为物理温度已经达标的证据。

验收：全部历史 trial 的分类、有效参数与下一候选可复核；预期降低 Approach 能量的候选确实通过 preview 驱动相应逻辑请求。低侧失败不误走高侧保守分支，缺失 Hold 指标不被当成零波动，没有强制时间切换伪造达标。通过要求由 R4 判定。

### R3：实现有条件的 Approach 延长

只有同时满足以下两个产品前提，才具备延长资格：

1. 已到达该候选分支实际允许的 Approach 下限。
2. 在原最长允许时间内仍无法完成。

延长判定必须基于候选及 effective parameters、实际逻辑请求和时间证据，不能凭 MOS PWM 较低、参数名为 floor 或一次普通超时触发。原期限、起算时间、下限来源和未完成原因必须留在同一 trial 审计中。

- 未满足两个前提的普通候选继续执行原停止/验收规则。
- 延长不能由传感器、PD/PPS、通信、取消、事件背压或 EEPROM 故障触发；已有安全拒绝始终停热。
- 延长须有明确有限上限，并计入原单目标 `20min` 预算。旧方案 `180s` 是整轮 stage timeout，不能直接当成 Approach 上限。
- 延长不能在试验中偷偷改变候选参数、身份、Hold 入口或温度目标。更换候选仍须在安全 trial boundary 重新 preview 并读回。
- 原期限未达的事实不得被删除，时间不得重置，也不得以伪造 phase 或稳定窗口掩盖超时。
- 单个候选失败只能证明该候选在该设备上的实测表现；不得据此断言所有参数都不可行或硬件极限已经被证明。

验收：分别证明未到下限不延长、未到期限不触发、符合两个前提才有资格、安全故障不延长、延长绝对上限停止和预算不重置。生产循环与报告必须使用同一真实单调时间。完整例外政策收敛前，条件延长代码不得启用。

### R4：贯通判定、确认与保存

- 原普通路径的时间门禁保持有效。条件延长属于限定例外，不能把全部 `5s/10s` 门槛改成软目标。
- 连续 `10s` 稳定窗口（目标 `±1.5°C`、至少 `3Hz`）、过冲 `<=3°C`、qualified Hold 峰峰值 `<=3°C`、`12s` scout 与完整 `60s` confirm 继续要求真实证据。qualified Hold 沿用既有温度和 phase 观察起点，起点之后的离带样本不得删除。
- 停止、评分、候选比较、确认资格、candidate-ready、seal、confirm-save 和 host 报告验证必须一致；不能只放宽某一环节。
- 延长候选的确认、通过和保存规则属于待定项。收敛前不得因“继续取得样本”自动升格、进入确认或写入 EEPROM。
- EEPROM 保存继续绑定 `runId + candidateId + candidateHash + powerClass`，使用既有原子保存/readback receipt；二次确认不重新调优。

验收：任一 gate 不满足时不能沿另一入口绕过；scout 成功仍须完整确认。身份、bank、trace 或持久化不匹配均失败；未获保存授权不得自动保存，取消和故障均停热。例外路径的验收需在待定项收敛后补齐。

### R5：保持标准报告并补齐整改证据

- 保留已确认的 `thermal_tuning_v2_report_template`、标准采样/结果输入与标准生成命令。示例只填合理 Mock 数据，实际报告与示例共用生成和渲染流程。
- 保留五文件、全部 trial、raw/report runs、sequence/digest、候选和保存 receipt。图表在视口允许时最小宽度约 `780px`，不足时适应可用宽度；四张设备本地图保留阶段边界/时间标签，温度图保留交点温度标签、阶段时长及稳定带，试验切换和跨图联动保持已确认行为。
- 每个 trial 显示候选范围、effective floor、下限来源、逻辑请求和最终 MOS PWM；缺失字段结构化 unavailable，不能靠当前策略倒填旧数据。
- 条件延长政策收敛后，在 ledger/bundle/页面明确显示两个触发前提的证据、原期限、允许延长的有限上限、实际延长时间、停止原因及资格处置。字段命名须先与设备事件和 schema 对齐，不能仅在 HTML 临时拼接。
- 保留温度/phase 与 qualified Hold 的区别、完整稳定及保温样本。PPS 电流只表示合同安全 ceiling，不伪造外部实测电流或功率。

验收：正常、失败、缺失证据和条件延长样例均走标准生成路径；选中 trial 的卡片、全部图和 ledger 同步。历史报告不得被重算为通过；真实报告的文件和设备 trace digest 可复核。UI 改动按既有视觉证据流程验证。

### R6：按提交节奏完成 HIL 与参数优化

- 按独立问题提交，英文 Conventional Commits、`--signoff`、保留 hooks；不做单个大提交或捎带无关改动。
- 每个包含固件代码修改的提交，先完成对应软件验证与构建，再按已有精确端口授权烧录该提交的产物并完成相关 HIL；未完成该轮 HIL 不宣称问题修复。
- 固件身份必须同时给出可读版本、提交、构建/产物身份和对应运行记录。烧录后先确认应用启动、授权串口、PPS 合同、有效热模型、100w/pps5a、HOT=LOW 与 heater 安全状态，再开始调优。
- 先验证 60°C 的完整 scout/batch/60 秒确认，再执行默认九目标完整资格范围。诊断范围成功不能代替九目标资格通过；失败 endpoint 不影响独立 endpoint，但依赖该 endpoint 的内部目标继续阻断。
- 60°C 每轮从 `<=35°C` 开始，冷却全程 MOS 断开、风扇全速；终止后继续全速到 `<35°C`。加热风扇使用既有 HOT=LOW；不通过改风扇算法掩盖调优问题。
- 实机失败保留完整标准报告并据证据修正；完整默认范围、安全失效及匹配的 EEPROM receipt 均具备后才可声称交付资格满足。

验收：每个固件提交有对应精确产物和实机运行证据；软件结果、诊断 HIL、默认资格和保存结果分别记录。端口消失、变化或占用立即停止，不自动换设备。真实 MCU 和外部 HUB 操作继续遵守项目授权边界。

## 实施前待定项

| 项目 | 必须明确的结果 | 未收敛时的边界 |
| --- | --- | --- |
| 延长计时 | 延长单次 Approach phase、full-speed-to-stable 的窗口起点期限，或两者分别处理；各自起算和结束时刻 | 不能混用参考曲线时长、phase 时长和稳定窗口计时 |
| 有限延长上限 | 最大延长量及一次或逐步延长规则；与整轮 stage timeout 和 `20min` 预算的关系 | 不启用无限等待，不把 `180s` 直接作为 Approach 上限 |
| 资格与保存 | 满足条件例外后的 scout 是否可确认、confirm 是否可通过以及是否可保存；报告如何记录原期限未达 | 不自动升格、不自动保存，不将例外泛化到普通超时 |

上述项目须给出具体方案、差异、风险及验收影响后由主人收敛。R1、证据分析、与旧方案一致的实现缺陷修正可独立推进；依赖例外政策的 R3/R4 部分只能在收敛后实施。

## 提交顺序与范围外事项

1. 固定本合同并审计 R1，建立基线差异与证据矩阵。
2. 按 R2 修复已证实且不改变算法设计的候选/生效缺陷，每个固件提交完成对应 HIL。
3. 收敛待定项，同步长期 SPEC，再按 R3/R4 实现并验证条件例外。
4. 按 R5 同步事件、schema、标准报告和必要 UI 证据。
5. 按 R6 完成 60°C 确认、九目标调优、安全失效和持久化验证，收口至原交付目标。

无 `--engine` 的外部主控 CLI 与其四文件报告保持原行为。PD 模块、PPS/PowerState 语义、3A 调优、`thermal_plant_auto`、RTD/ADC 校准和主动冷却参与加热控制均不在此次整改范围。确需改变生产控制算法时先研判，不作为“实现修复”直接夹带；独立问题只在主人明确要求后移交新对话/新 PR。
