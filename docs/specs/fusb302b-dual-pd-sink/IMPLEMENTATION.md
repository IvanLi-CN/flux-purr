# Implementation

## Firmware

- `firmware/src/adapters/pd.rs` defines controller-neutral contract types, source-capability parsing, contractual power calculations, the `20V/3A` performance threshold, and FUSB302BMPX PPS selection within the `5V..28V` absolute guard and live APDO with fixed-PDO fallback. Public Fixed/PPS requests reject currents outside `3A..5A` and voltages outside the Fixed `5V..20V` or PPS `5V..28V` guards before exact capability selection.
- `firmware/src/adapters/fusb302b.rs` owns Flux Purr's pure FUSB302B sink policy: PPS and fixed RDO encoding, source-capability decoding, PPS keepalive renewal, and contract state. It does not own FUSB302B register access or FIFO framing. The validated FUSB302BMPX PPS path uses `PdRevision::Rev30` for automatic GoodCRC and every locally initiated PD header, so a PPS-capable source can advertise and accept APDO contracts. The policy does not authorize heat until `Accept` and `PS_RDY`; detach/reset/reject/wait/fault clears its contract. An unchanged PPS RDO is a bounded liveness probe: lack of a source-level `Accept`/`PS_RDY` response expires only the probe marker while confirmed VBUS remains authoritative; FUSB302B VBUS loss, transport fault, or protocol reset still revokes the contract fail-closed. Startup and automatic idle select the lowest adequate Fixed PDO under the standby budget. A live PPS contract descends in bounded `500mV` steps with `500ms` spacing and ends in an explicit Fixed request before idle is confirmed. Equivalent Idle tickets join both an in-flight exchange and a confirmed intermediate step without restarting its spacing timer. Fresh PPS renewal replies advance the Source message sequence while preserving the active contract; GoodCRC echoes the Sink sequence and is excluded.
- `firmware/src/bin/flux_purr.rs` dispatches production PD traffic through `pd_service_task`, a dedicated normal-executor Embassy task. It requires two stable Device ID reads matching an accepted FUSB302 form (`0x8x` or `0x9x`) plus a readable status bank; all other responses become `unknown` with zero PD writes. The identity check only establishes that the shared I2C address is the expected PD controller; every accepted device uses the same PD 3.0/PPS policy path. Before sink toggle it configures default host current, disables CC measurement, and installs the toggle interrupt mask; after attachment it measures the selected CC pin and installs the receiver interrupt mask. The ESP32-S3 native async I2C driver is shared by the PD and EEPROM users, so each bounded physical transaction yields through the I2C interrupt future instead of blocking the normal executor, and the task owns its `5ms` `EmbassyTimer` cadence. The PD task owns the FUSB302 runtime and a non-blocking I2C device; it attempts an immediate bus try-lock at the start of each turn, skips the turn without waiting or consuming mailbox commands when EEPROM owns the bus, and retries on the next tick. Once acquired, it owns one bounded command-plus-poll turn, reads the non-destructive FUSB302 status bank, publishes the status-verified snapshot, releases the bus, and records the PD heartbeat. The Front Panel task sees only snapshots and sends non-blocking mailbox commands. EEPROM record restore, record writes, raw maintenance reads/writes, snapshot reads/digest, and verification release the async-arbitrated shared bus after each bounded physical transaction or chunk; the mutex critical section covers only lock state, and a successful EEPROM commit is never synchronously mirrored to flash.
- FUSB302BMPX currently observes a `5V..21V` PPS APDO with fixed-PDO PWM fallback; calibration requires a qualifying PPS contract. The adapter applies the operational `5.5V` floor and absolute `28V` ceiling before the live APDO boundary, retains every usable APDO for manual and automatic request selection, and never imports the archived controller's `21V` ceiling. A pending FUSB contract starts the normal runtime with heater output interlocked and drains bounded completed PD frames each service turn. Every absent Source Capabilities response remains bounded `Get_Source_Capabilities` retry without a Sink PD reset.
- An explicit PPS request retained across a Fixed-to-PPS capability refresh is PPS-only. If the fresh Source Capabilities do not contain a matching APDO, the request completes as `Rejected`; the adapter never substitutes a Fixed RDO for a requested PPS contract.
- `PdContractRequest` fields are private to the firmware crate and public construction validates the protocol's exact Fixed/PPS voltage and current increments, including the operational `5.5V` PPS floor. The capability selector revalidates requests before selection. Confirmed active state is projected only when the current Source Capabilities still represent the negotiated PDO/APDO; stale or empty capability evidence therefore projects `CapabilityInvalidated`/`Fault` and cannot authorize heat. Confirmed PPS state retains a private source-capability slot alongside the public adjustment range, so heater control treats a step as continuous only when exact request selection resolves to that same APDO, including when source ranges overlap.
- Power-domain state is published through a coalescing `Watch`; terminal ticket outcomes use a bounded channel and per-ticket reply slots. Boot display transfers and runtime consumers use the typed state subscription instead of polling `PdService` status.
- `PowerState` reports `PowerProtocol::Fault` with `PowerFailure::CapabilityInvalidated` whenever a fresh observation is not represented by the current Source Capabilities, so a capability-generation mismatch cannot look like a ready contract to consumers.
- A skipped PD turn caused by shared-I2C contention clears the published observation and heater permit but does not settle or discard a pending Contract/Idle/Refresh ticket; the next acquired turn resumes that operation.
- `PowerState.requested` is populated only for an explicitly pending request, while `PowerState.active` is populated only from a confirmed capability-backed observation; a confirmed contract is never reclassified as a new request.
- Automatic heater capacity derives its source voltage interval only from a connected APDO component. When the runtime needs one current ceiling for that interval, it uses the lowest available current at its APDO boundaries, so a higher-current APDO at the top voltage cannot overstate available power at lower requests.
- VIN ADC calibration derives the request current from the APDO covering each voltage in the sweep, including after crossing mixed-APDO boundaries.
- `HeaterPowerBackend` carries terminal thermal-calibration disarm state through PPS and fixed-PDO fallback representations. Capability refresh and fallback-to-PPS rediscovery preserve it; only the explicit manual PPS re-arm path clears it.
- The FUSB302B runtime treats local `RETRY_FAIL`, pending-contract timeout, and partial FIFO timeout as CC-preserving recovery: it clears the active contract and cached capabilities, flushes only the receive FIFO, and returns to bounded `Get_Source_Capabilities` discovery. It sends that request after an explicit fixed-to-PPS transition, but never as an unsolicited liveness probe for an active fixed contract. A failed transmit additionally flushes the TX FIFO so an incomplete frame cannot poison the next query. `RETRY_FAIL` recovery precedes every queued receive frame. After `RETRY_FAIL`, it consumes the latch until the next bounded query transmit clears it. Received PD resets also retain Rd and the configured PHY. Any observed low VBUS immediately interlocks heating and invalidates the cached contract; only a `VBUSOK` transition starts the `50ms` continuous-low confirmation before entering a VBUS-restore wait. During that wait the runtime retains the selected CC/RX session and, after VBUS returns, resumes bounded Source_Capabilities discovery without reinitializing the PHY or restarting CC toggling. VIN sampling updates measured telemetry and thermal-model inputs without changing PD authorization. Fixed and PPS contracts are never invalidated by a VIN deficit; normal PPS current limiting can lower delivered voltage without canceling the accepted request. A VBUS-restore guard prevents repeated PHY initialization while VBUS remains absent. A capability refresh that still covers the active contract only updates the cache and does not re-request the same contract. `STATUS0.BC_LVL` cannot prove a Sink detach (`00` can report Ra), so low, active, and unknown status retain Rd and the current PD session.
- Startup configures the active-low backlight before any potentially blocking bus work, initializes the FUSB302B policy, and starts the independent normal-executor PD task before the bounded initial Sink startup window. The window reads service health independently of contract availability: the starting service remains eligible to negotiate before its first contract snapshot. After heap initialization, ordered one-shot Embassy boot stages transfer one boxed pipeline between PD, display, EEPROM, runtime preparation, and runtime-finalization work; no stage moves a complete boot state through a guarded task stack. Display init and startup-frame flush retain their one-second timeout and only apply the latest PD snapshot while the PD task continues its own `5ms` cadence. This keeps the initial attachment, source-capability retry, request timeout, and PPS keepalive deadlines independent of the Front Panel task.
- The runtime main loop never polls or mutates the FUSB302B runtime. It consumes subscribed state changes or a bounded `5ms` input/safety tick, then applies its local `PowerState` before USB/LAN, thermal, persistence, and display work; each pass consumes at most `256` USB bytes and one complete USB or LAN control command. Voltage requests are non-blocking power-domain submissions, including automatic-idle restoration after a manual override, failed adjustable request, or terminal disarm. While a PPS adjustment is waiting within the confirmed APDO at the same operating current, the last confirmed contract remains observable and heater PWM is not cleared; discrete voltage increases and mode changes clear PWM in the heater controller before submission. Contract loss is fail-closed both through the task-owned physical heater permit and the main-loop state reconciliation.
- Ready PD snapshots expire after `100ms`. The main loop clears the physical heater gate when no fresh snapshot is available, the PWM gate checks the monotonic expiry before every write, and the watchdog supervisor checks it independently at `50ms` cadence so a stopped PD or Front Panel task cannot leave a permit valid indefinitely.
- A source `Reject` or `Wait` before `PS_RDY` cancels the pending request and returns to `WaitingForSourceCapabilities`, allowing the existing bounded re-query path to retry without withdrawing CC. If a later renegotiation is rejected while an active contract exists, the policy returns to `Ready` and preserves that contract.
- Source-capability discovery and recovery use only the FUSB302B sink policy. They do not depend on thermal-tuning state or candidate data.
- When a pending contract becomes ready, the runtime clears any UI or calibration heater arm intent captured before readiness; heating can resume only after a new explicit arm operation.
- After the bounded VBUS-restore confirmation, `resynchronize_after_vbus_restore` resets only the PD protocol engine, flushes both FIFOs, reapplies the receiver PHY configuration and interrupt masks, and resets the local transmit message ID. It preserves CC pulls and does not restart Type-C toggling before bounded `Source_Capabilities` discovery.
- `firmware/src/board/s3_frontpanel.rs` reserves `GPIO7` as `PIN_PD_INTERRUPT` and includes it in the active GPIO map.
- Firmware status emits contract metadata separately from the legacy `currentMa` telemetry field. `pdContractCurrentMa` and `pdContractPowerMw` are contractual upper bounds, never a physical-current claim.
- Contract callers consume each accepted ticket's terminal outcome, so reply slots are released after completion. Long-running product operations await their tickets; manual PPS retains its ticket in `ManualPpsState` and consumes the result non-blockingly on a later control pass. Coordinator arbitration retains the confirmed owner priority, rejects lower-priority replacement requests as `Superseded`, and treats `Idle` as an explicit release transition. A `Confirmed` ticket is emitted only after the current service turn has produced a fresh status observation; capability refresh also reaches a terminal result on detach/fault, while timeout and source rejection remain distinct outcomes.
- The PD service gives an admitted replacement command precedence over retrying a deferred operation. This prevents a request already settled as `Superseded` from being retransmitted before the replacement, including an explicit idle restoration, is applied.
- A replacement Contract, Idle, or Refresh command uses a fresh Source_Capabilities transaction after clearing the old receive FIFO and refresh markers. Duplicate or older Source_Capabilities message IDs are rejected before they can replace the cached generation or emit a new RDO; the modulo-eight half-range is treated as ambiguous rather than fresh. A canceled queued replacement explicitly aborts any still-pending protocol operation before its ticket settles. `Accept`/`PS_RDY` responses from the abandoned transaction are ignored before the new capability message starts the replacement request. `PdServiceClient` always submits owner requests through `PowerCoordinator`; it does not reuse a snapshot ticket or report an active contract as a newly acquired owner intent.
- Explicit refresh completion is gated on the post-capability policy phase: a refresh remains pending through `WaitingForAccept`/`WaitingForPsRdy`, while a valid active contract uses the cache-preserving refresh path without a duplicate RDO. Refresh timeout clears the active contract and cached capabilities, then records `TimedOut` before any subsequent request can reuse stale power state.
- Coordinator cancellation fences a superseded mailbox command before it reaches FUSB policy; a replacement is retained for bounded retry after the private mailbox drains, and stale terminal state is not projected.
- Deferred replacement storage is single-slot and lossless for accepted tickets: a second mailbox admission receives a terminal transport failure without overwriting the already-deferred command.
- Idle restoration requests do not reuse a one-shot pending ticket; each caller enters Coordinator admission or observes an already-confirmed idle state.
- Standby current selection and PPS descent are implemented: descent retains the confirmed PPS operating-current limit within the active APDO, and the final Fixed request applies the `5W` standby budget. Standby voltage is selected from advertised Fixed capability and budget alone. The VIN-driven qualification state, measurement window, and voltage-escalation updates are removed.
- Preparation includes pending physical disarm in its heating field. Readiness and disarm completion use fresh confirmed-contract and applied-output facts, with no VIN tolerance, stability, or calibration prerequisite.
- Cooling requests use the PD service's bounded PPS-to-Fixed transition with a `12V` minimum. Physical fan output waits for its confirmed working contract, and fan pulse gaps retain working intent. Preparation retains necessary cooling before selecting standby power. It exits manual VIN/RTD/heater-curve calibration modes as well as canceling running jobs, while leaving persisted calibration and completed-job data intact.
- The preparation hold consumes its own Idle ticket and retries terminal protocol failures. Equivalent Idle requests retain the current protocol exchange and ramp timing instead of interrupting the same descent. The hold, ticket settlement, cooling behavior, and protocol confirmation boundary remain independent of VIN measurement.
- While preparation is held, the physical heater backend submits no power requests. Coordinator admission rejects thermal/manual/calibration contracts and explicit capability refreshes before they can preempt Idle; cooling Idle requests remain available. A stale rejected or canceled command cannot clear a different pending Idle ticket in the PD service.
- The runtime reads the latest watched power state before projecting its contract and readiness. Display I/O can consume the same receiver's notification while maintaining the heater interlock, so notification consumption alone cannot leave the runtime on an older PPS or Fixed snapshot.
- A newly admitted command supersedes a deferred replacement according to owner priority, settling the displaced deferred ticket instead of replaying an older intent after the mailbox drains.

## Host And Console

- `flux-purr-devd` preserves and relays the new status fields while retaining its legacy `currentMa` compatibility behavior for existing calibration validation.
- Web transport adapters preserve the fields across devd, serial, and LAN sources.
- The control console presents controller type, contract type, contractual current/power, and guarantee/degraded state in its PD contract status detail.

## Verification

- Firmware adapter tests cover exact Fixed/PPS alignment and malformed request rejection, APDO selection across overlapping ranges, deferred-command and failed-owner queue supersession ordering, PPS/fixed-RDO framing, PPS renewal, `20V@3A=60W`, `20V@5A=100W`, lower-voltage degraded operation, `Accept`/`PS_RDY`, detach/reset, rejected contracts, and source-capability packet decoding. The upstream crate validates FUSB register access, device identification, PHY configuration, FIFO framing, and full-FIFO receive handling through its public API.
- Control-plane, devd, and Web verification run from repository-native test/build commands.
- A source-boundary regression covers both boot and runtime VIN sampling and forbids access to PD or physical heater-control authority. It failed on the former VIN contract interlock before its removal. Focused host regressions cover protocol-only readiness with zero, biased, and nominal VIN readings, protocol-only terminal disarm, stale-request rejection during preparation, and calibration cancellation without replay. FUSB adapter regressions retain `Accept`/`PS_RDY`, rejection, renewal, standby selection, and fan power admission coverage.
- Complete idle is reconciled after applying the fan policy and physical fan command, for ordinary operation and explicit preparation alike. Manual PPS exit and normal cooling completion restore the lowest adequate Fixed PDO without calling `prepare_flash`. Armed zero-PWM ticks, fan pulse gaps, active calibration and pending output work retain their working supply. The idle heater-output path drops cached working-contract state and submits no competing PPS request; a fresh output start reconfirms its working contract.
- Product HIL uses the ignored `native_product_fixed_idle_hil` fixture in `tools/flux-purr-devd/src/product_hil_tests.rs`, with the normal devd serial session and explicit target/source identities. The `product-sequence` action covers ordinary manual-PPS exit and heating/cooling completion without preparation, then explicit preparation hold and cooling. It does not write VIN slot fits. It checks device protocol state and IsolaPurr `port_c`, verifies applied outputs and unchanged persistent calibration, and asserts Fixed 5V after runtime restoration before recording success. Source-side VBUS observations are evidence only. `FLUX_PURR_HIL_HEAT_MV=21000` selects a cold-heater PPS `21V@3A` load case and checks that the accepted contract and uptime survive source current limiting; the default `8000` point retains the lower-power heat/cooling case. Both use temporary manual output and do not establish ordinary production heater arming or a persisted thermal model.
